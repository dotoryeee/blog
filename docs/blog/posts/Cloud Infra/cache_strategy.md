# 캐시 전략 정리

<!-- more -->

## 캐시란
캐시(Cache)란 원본보다 빠른 저장소에 결과를 복제해 두고 같은 요청을 원본까지 보내지 않고 끊는 계층

- 전제: 같은 데이터가 반복 조회돼야 함 → 아니면 적중률이 낮아 계층만 늘어남
- 대가: 원본과 캐시가 서로 다른 값을 가질 수 있는 구간이 생김
- 판단 기준: 적중률, 갱신 빈도, 오래된 값을 얼마나 견딜 수 있는가
- 성격: 성능 개선 수단이지 저장소가 아님 → 사라져도 서비스가 죽지 않아야 정상

---

## 읽기 전략
캐시에 없을 때 누가 원본을 읽어 채우느냐로 갈림

| 전략 | 동작 | 장점 | 단점 |
|------|------|------|------|
| Cache-aside | 앱이 캐시를 먼저 보고, 없으면 직접 원본을 읽어 캐시에 씀 | 캐시가 죽어도 앱이 원본으로 우회 가능. 필요한 키만 적재 | 캐시 접근 코드가 앱에 흩어짐. 최초 조회는 항상 느림 |
| Read-through | 앱은 캐시만 보고, 없으면 캐시 계층이 원본을 읽어 채움 | 앱 코드가 단순. 적재 로직이 한 곳에 모임 | 캐시 계층 장애가 곧 조회 실패. 라이브러리·제품 의존 |

- 실무에서 가장 흔한 것은 Cache-aside → 캐시를 부가 계층으로 두는 구조라 장애 내성이 높음
- 최초 조회가 느린 문제는 미리 채워 두는 방식으로 완화

---

## 쓰기 전략
쓰기 시점에 캐시와 원본을 어떤 순서로 다루느냐로 갈림

| 전략 | 동작 | 장점 | 단점 |
|------|------|------|------|
| Write-through | 캐시와 원본에 동시에 씀 | 캐시가 항상 최신. 읽기 일관성 좋음 | 쓰기 지연이 원본 쓰기에 묶임. 안 읽힐 데이터도 캐시에 쌓임 |
| Write-back | 캐시에만 쓰고 원본 반영은 나중에 모아서 | 쓰기가 빠르고 원본 부하가 줄어듦 | 캐시가 유실되면 아직 안 내려간 쓰기도 같이 사라짐 |
| Write-around | 원본에만 쓰고 캐시는 건드리지 않음 | 안 읽힐 데이터로 캐시가 오염되지 않음 | 새 키는 첫 조회가 미스, 기존 키는 옛 값이 적중해 삭제를 병행해야 함 |

- Write-back은 유실 위험을 감수하는 대신 쓰기 처리량을 얻는 선택 → 손실이 허용되는 데이터에만
- 읽기·쓰기 전략은 독립적으로 조합 가능 → Cache-aside와 Write-around를 묶는 구성이 흔함

---

## 무효화
캐시가 틀린 값을 들고 있는 시간을 얼마나 줄일지의 문제

| 방식 | 동작 | 적합 |
|------|------|------|
| TTL 만료 | 정해진 시간이 지나면 스스로 사라짐 | 오래된 값을 얼마간 견딜 수 있는 데이터 |
| 명시적 삭제 | 원본을 고칠 때 해당 키를 지움 | 갱신 지점이 분명하고 키를 특정할 수 있을 때 |
| 버전 키 | 키에 버전을 붙여 갱신 시 새 키를 씀 | 지울 키가 많거나 목록형 데이터 |

- TTL만으로는 만료 전까지 틀린 값이 그대로 나감 → 정확도가 중요하면 명시적 삭제를 병행
- 명시적 삭제는 지울 키를 빠뜨리면 조용히 틀린 값이 남으므로 삭제 실패 시 재시도 경로가 필요
- 버전 키는 지우지 않고 갈아타는 방식이라 삭제 누락이 없는 대신 옛 키가 메모리에 남음

---

## 장애 유형
캐시가 무너지는 방식이 세 가지로 갈리고 대응책도 각각 다름

| 유형 | 무엇이 일어나는가 | 대응 |
|------|-----------------|------|
| 캐시 스탬피드(Cache Stampede) | 인기 키 하나가 만료된 순간 동시 요청이 전부 원본으로 감 | 뮤텍스로 한 요청만 재계산, 만료 전 미리 갱신 |
| 캐시 관통(Cache Penetration) | 캐시에도 원본에도 없는 키를 계속 조회해 캐시가 채워지지 않음 | 없음을 짧은 TTL로 캐싱, Bloom filter로 사전 차단 |
| 캐시 눈사태(Cache Avalanche) | 많은 키가 같은 시각에 만료돼 원본에 부하가 몰림 | TTL에 무작위 편차를 더해 만료 시점을 흩뜨림 |

- 스탬피드는 키 하나, 눈사태는 키 다수 → 증상은 비슷해 보여도 원인이 다름
- 관통은 존재하지 않는 키가 원인이라 TTL을 늘려도 해결되지 않음
- 세 가지 모두 원본이 버티지 못할 때 드러남 → 캐시 앞단이 아니라 원본 쪽 한계를 같이 봐야 함

---

## 일관성
캐시와 원본을 동시에 바꿀 수 없어서 생기는 문제

- 원본을 고치고 캐시를 지우는 순서가 기본 → 반대로 하면 지운 직후 옛 값이 다시 실릴 수 있음
- 그럼에도 조회와 갱신이 엇갈리면 옛 값이 다시 적재되는 구간이 남음
- 재적재 구간을 더 좁히려면 갱신 후 짧은 지연을 두고 한 번 더 지우는 방식을 씀
- 이때 지연이 조회와 적재에 걸리는 시간보다 길어야 효과가 있고, 그래도 완전한 보장은 아님
- 캐시는 결국 최종 일관성 → 강한 일관성이 필요한 값은 캐시에 두지 않는 편이 안전
- 쓰기가 잦고 읽기가 드물면 캐시가 적중률 없이 무효화 비용만 만듦

---

## 선택 가이드

| 상황 | 추천 방식 | 추천 사유 |
|------|---------|---------|
| 읽기가 압도적으로 많고 갱신이 드묾 | Cache-aside + TTL | 구현이 단순하고 캐시 장애에 강함 |
| 방금 쓴 값을 즉시 읽어야 함 | Write-through | 쓰기 시점에 캐시가 최신으로 맞춰짐 |
| 쓰기가 폭발적이고 유실을 견딜 수 있음 | Write-back | 원본 쓰기 부하를 모아서 낮춤 |
| 쓰고 나서 잘 안 읽는 데이터 | Write-around | 안 읽힐 값으로 캐시가 차지 않음 |
| 인기 키에 요청이 몰림 | 뮤텍스 또는 만료 전 갱신 | 만료 순간 원본으로 몰리는 것을 막음 |
| 존재하지 않는 키 조회가 많음 | 없음 캐싱 또는 Bloom filter | TTL 조정으로는 안 풀림 |
| 대량 키를 한꺼번에 적재 | TTL 무작위 편차 | 같은 시각 동시 만료를 흩뜨림 |

---

## 결론
- 캐시 전략을 고른다는 것은 적중률과 오래된 값을 견디는 정도를 맞바꾸는 일
- 읽기는 Cache-aside가 기본이고, 쓰기 전략은 유실을 견딜 수 있는지로 갈림
- 무효화는 TTL만으로 부족해 명시적 삭제나 버전 키를 겹쳐야 함
- 스탬피드·관통·눈사태는 증상이 비슷해도 원인이 달라 서로의 대응책으로 대체되지 않음
- 캐시는 사라져도 서비스가 살아 있어야 하는 계층이므로, 없을 때 동작하는지를 먼저 확인할 것
